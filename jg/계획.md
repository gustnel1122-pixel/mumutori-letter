## 1. 전체 구조

```
[카메라 감지 레이어]                [디렉터(상태 판정)]              [캐릭터 7개 독립 액터]
 얼굴비율/몸높이비율(이미 있음)  →   거리 0~3단계 판정        →      각자 유틸리티 AI 또는
 (index.html의 handleFace/        (레벨 0/1/2/3)                   공유 이벤트에 반응
  BodyDetections 그대로 재사용)                                     → 애니메이션 클립 선택
                                                                      → 캔버스 합성(위치 고정)
```

- **레벨 0(없음)**: 사람 미감지. 캐릭터마다 독립 유틸리티 AI로 일하기/쉬기/말걸기를 스스로 고름.
- **레벨 1(먼 거리, 지금의 THRESH=0.15와 동일 문턱)**: 전원 "올려다보기/쳐다보기" 클립으로 전환(이미 있는 동작), 유지 후 레벨 유지되면 가끔 다시 쳐다봄.
- **레벨 2(가까움, 새 문턱 — 예: 얼굴비율 0.28 또는 몸높이비율 0.55)**: "씨앗 던지기 놀이"(명칭 확정 전) — **전원이 유리창(=손님 얼굴)을 향해 각자 씨앗을 던진다**(원본 기획서 2026-11-03 그대로, 캐릭터끼리 싸우는 게 아니라 손님에게 다 함께 "장난"을 거는 그림). **해바라기씨만 태연**하게 지켜본다(원본 기획서에 이미 있는 설정, 성격과도 맞음). 씨앗 바주카는 사장님이 오늘 새로 더한 소품으로, 전원 던지기 위에 추가 효과로 둔다(아래 캐릭터표 참고).
- **레벨 3(매우 가까움, 지금의 BODY_HEIGHT_RATIO_THRESH=0.45보다 큰 값 — 예: 0.70)**: 전원 "도망" 클립 → 책상 밑에 숨는 정지 포즈 → 사람이 멀어지면(레벨 0 복귀 후 쿨다운) 살짝 고개만 내밀고 복귀.
- 레벨 전환은 지금 index.html의 `faceHistory`식 흔들림 견디기(최근 N번 중 M번)를 그대로 레벨마다 적용해 깜빡임을 막는다(이미 검증된 패턴 재사용).

### 캐릭터 액터 하나의 내부 구조 (유한상태기계 + 작은 유틸리티 AI)
레벨 0에서만 작동하는 개별 행동 선택기:
- 욕구 점수 3개: `일함`(시간 지나면 증가), `쉼`(일함이 높을수록 증가), `말걸기 욕구`(관계도 쌍이 둘 다 idle일 때 증가).
- 매 틱(예: 3~5초)마다 가장 높은 점수 + 약간의 무작위를 더해 행동 선택 → 선택된 행동 클립 재생 끝나면 그 욕구를 리셋.
- 예외: 전역 레벨이 0이 아니면 개별 유틸리티 AI는 일시 정지하고 디렉터 지시를 그대로 따른다(레벨 0으로 복귀하면 다시 개별 AI 재개).

- **씨앗 바주카**는 "전원 던지기" 위에 사장님이 오늘 새로 더한 **추가 소품 효과**로 둔다(필수 아님) — 아래 설명 참고.

- **씨앗 바주카(사장님 지정)**: 캐릭터가 드는 게 아니라 **소품 자체가 독립된 오브젝트**로 존재(예: 창가 선반에 거치). 레벨 2가 되면 바주카 소품 자신의 애니메이션(조준→발사→반동)이 재생되고, 해바라기씨/도토리는 "신호를 주는" 정도로 짧은 손짓만 한다(짧은 팔 범위 안에서 가능 — 손가락 없이 툭 치는 동작 정도).
- **던지기**는 기존 "던지기" 클립(짧은 팔로 작은 씨앗 하나를 앞으로 톡 던지는 동작, 땅콩이 돋보기를 드는 것과 같은 수준의 짧은 팔 동작)으로 충분 — 바주카와 별도로 둘 다 쓸 수 있음(사장님 선택 사항으로 남김).

## 3. 열린 질문 (사장님 확인 필요 — §6 참고)
1. (가벼운 확인) "씨앗전쟁"은 원본 기획서(11/3)처럼 **전원이 손님에게 씨앗을 던지는 깜짝 게임**으로 이해했는데, 맞는지. 캐릭터끼리 싸우는 그림이면 세계관 규칙(§1-4-3 "악당·싸움 없음")과 부딫히므로 그 경우만 다시 의논이 필요.
2. 땅콩(MD) 자리를 "카운터 옆 품평 책상"으로 새로 정해도 되는지(정본에 땅콩 자리가 없음).
3. 씨앗 바주카 소품의 생김새(선반에 거치된 장난감 대포 느낌 등)를 새로 만들어야 하는데, 이것도 "새로 그리지 않기" 원칙의 예외로 **소품만** 새로 그려도 되는지, 아니면 기존 소품(상자·펜 등)을 변형 없이 조합해서 표현해야 하는지.

## 4. 성능 계획 — 갤럭시 탭(→ 실제는 LG 울트라탭 10A30Q)에서 초당 30프레임

### 4-1. LG 울트라탭 10A30Q 기준 성능 예산 (2026-11-17 23:00 추가)
- 스냅드래곤 680(옥타코어, 중급 Adreno GPU)·램 4GB는 갤럭시 탭 S급(스냅드래곤 7~8급)보다 한 단계 아래 보급형 — 아래 성능 목표를 더 보수적으로 잡는다.
- **동시 처리 예산(안 기기 기준)**: 얼굴 감지(GPU) 7회/초 유지 + 몸 감지는 **기본 꺼짐**(조절 화면에서 켤 때만, §0 1단계 코드와 동일) — 몸 감지까지 기본으로 같이 켜면 4GB 램 기기에서 감지 2종 + 캔버스 렌더가 경합할 위험이 큼.
- **2단계(사는 친구들) 캐릭터 수·효과 예산**: 이 기기에서는 3D 실시간 렌더링을 쓰지 않고(§4 표 그대로) 2D 투명 PNG 스프라이트 방식만 쓴다. 캐릭터 7명 전원을 투명 PNG로 그려도 "이미지 블릿"만이라 GPU 셰이더 비용이 없어 부담이 적지만, 1차 구현(D7 데모)은 **2명**으로 시작해 실기에서 fps를 재측정한 뒤 단계적으로 늘린다(한 번에 7명 다 넣지 않음).
- **씨앗/바주카 효과 개수 예산**: 레벨 2(씨앗 던지기) 때 화면에 동시에 떠 있는 "날아가는 씨앗" 스프라이트는 소수 기기 기준 **최대 4~5개 동시**로 제한 권장(파티클처럼 수십 개를 띄우지 않는다) — 투명 PNG 블릿이라도 개수가 늘면 비례해서 비용이 커짐.
- **감지 주기**: 1단계와 동일하게 감지는 `setTimeout` 틱으로 렌더(`requestAnimationFrame`)와 분리 유지 — 감지가 느려져도 캐릭터 애니메이션 자체는 끊기지 않게.
- 위 숫자는 전부 **실기(LG 울트라탭) 재측정 전까지는 잠정치**다 — 이 PC의 헤드리스 자동화 환경 숫자를 성능 확정치로 쓰지 않는다(§4-구체적 성능 설계 5번과 동일 원칙).

### 비교: 2D 스프라이트(클립) 방식 vs 3D 모델 실시간 렌더링

| 기준 | 2D 스프라이트/클립 방식 (관절 방식 재활용) | 3D 모델 실시간 렌더링 |
|---|---|---|
| 자산 준비 상태 | **7명 전원, 필요한 동작 이미 있음**(일하기·깜짝·올려다보기·던지기·도망, 11/4 v8) | **도토리 1명만 정본**, 나머지 6명은 "정본 아님"(사장님 승인 전) — 손님에게 못 보여줌 |
| 그림 신뢰도 | 공식 그림 그대로(이미 손님에게 공개된 idle/reaction mp4와 같은 화질) | 공식 그림과 "아주 조금 다름"(기록에 적힌 사실) |
| 갤럭시 탭 GPU 부담 | 캔버스 2D 블릿(이미지/비디오 프레임 그리기)만 — 쉐이더 없음. 지금의 카메라+크로마키 합성과 같은 종류의 작업만 몇 배 늘어남 | WebGL 스키닝·셰이딩·조명까지 매 프레임 — **지금 몸 감지(MediaPipe GPU 딜리게이트)와 같은 GPU를 나눠 써야 함** → 바로 몇 시간 전 아이패드 사파리가 GPU+메모리 과부하로 죽은 것과 같은 유형의 위험 |
| 안드로이드 영상 디코더 한계 | ⚠ 캐릭터마다 `<video>` 태그를 따로 쓰면 보급형 기기의 **동시 하드웨어 비디오 디코더 개수 제한(보통 3~4개)**를 넘길 수 있음 → 그래서 **영상이 아니라 투명 PNG 스프라이트 시퀀스**로 뽑아 캔버스에 그리는 방식을 권장(디코더 제한과 무관, 그림이라 단순 복사) | 해당 없음(원래 메시 렌더링) — 그러나 위 GPU 경합 문제는 그대로 |
| 결론 | **권장.** 오늘 밤 1단계와 같은 캔버스 합성 기법을 그대로 확장 | **지금은 쓰지 않음.** 6명 3D 승인 + 실기 GPU 여유 확인 뒤 재검토 |

### 구체적 성능 설계
1. 캐릭터 애니메이션 자산은 **비디오(mp4)가 아니라 투명 PNG 시퀀스(또는 스프라이트시트)**로 다시 뽑는다 — v8comp.py 파이프라인에서 "전체 합성 mp4" 대신 "캐릭터별 알파 PNG 프레임"을 추가로 출력하도록 렌더링 쪽(H드라이브 작업)에 요청해야 함(이 웹 작업과 별도 의존 작업, §5 일정에 반영).
2. 렌더 루프는 지금처럼 `requestAnimationFrame` 한 번으로 카메라+크로마키+캐릭터 7명을 한 번에 그린다. 캐릭터 그리기는 상태에 따라 현재 프레임 인덱스만 올리는 가벼운 연산(스프링 물리 재계산 없음 — 이미 영상 추출 때 다 계산돼 있음).
3. 감지(얼굴/몸)는 오늘 밤 코드처럼 `setTimeout` 기반 별도 틱(7회/초, 안드로이드는 늘릴 수 있는지 실기 확인)으로 렌더와 분리 유지.
4. 목표: 안드로이드 갤럭시 탭에서 렌더 30fps, 감지는 몸 감지 포함 7~15회/초면 충분(사람 반응이 "즉시"로 보이려면 0.3초 안에만 걸리면 됨 — 사람 눈에는 15회/초도 매끈함).
5. 이번 1단계 테스트에서 확인된 것(§7 참고): 이 PC의 헤드리스 Chromium 자동화 환경에서는 실제 GPU가 아니라 소프트웨어 렌더라 감지 속도가 느리게 나왔다 — **실제 갤럭시 탭에서 재측정 전까지 숫자를 확정 성능으로 쓰지 않는다.**
